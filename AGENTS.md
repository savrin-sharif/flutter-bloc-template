`flutter-bloc-init.sh`. Agents that support `AGENTS.md` load this file
automatically; for other tools, paste it before your feature request and API

## First: understand this project

Before changing anything:

   files under `lib/`, `test/`, and `docs/`.
2. Inspect `assets/envs/.env`, but never expose secrets or commit real secrets.
3. Confirm the generated package name from `pubspec.yaml`; never assume it is
   `flutter_bloc_template`.
4. Inspect `lib/core/config/app_config.dart`, `lib/core/network/dio_client.dart`,
   `lib/core/errors/failure.dart`, `lib/core/network/connectivity_service.dart`,

## Architecture contract

The project uses feature-first clean architecture:

```text
lib/
├── app/                         # Root application
├── core/
│   ├── config/                  # Environment selection
│   ├── di/                      # get_it composition root
│   ├── errors/                  # Typed Failure hierarchy
│   ├── logging/                 # LoggerService and HTTP logger
│   ├── network/                 # Dio, API error parsing, connectivity
│   ├── presentation/mixins/     # Shared BLoC behavior
│   ├── router/                  # go_router graph
│   └── theme/                   # Material/Cupertino themes
├── shared/                      # Existing cross-feature UI and utilities
└── features/<feature>/
    ├── data/
    │   ├── datasources/         # Dio/local persistence calls
    │   ├── models/              # JSON DTOs and mapping
    │   └── repositories/        # Domain contract implementations
    ├── domain/
    │   ├── entities/            # Framework-independent business objects
    │   ├── repositories/        # Abstract contracts
    │   └── usecases/            # Focused application operations
    └── presentation/
        ├── bloc/                # Events, immutable states, BLoCs
        ├── pages/               # Routed screens
        └── widgets/             # Feature-specific reusable UI
```

Dependencies point inward:

```text
presentation ──> domain <── data
       │                    │
       └──── core APIs ─────┘
```

- Domain must not import Flutter, Dio, JSON, widgets, or data-layer classes.
- Data implements domain repository contracts.
- Presentation calls use cases, not Dio or data sources directly.
- Register concrete implementations only in `core/di/injection.dart`.
- Always search `lib/shared/` before implementing a widget or UI utility. Reuse
  a suitable shared component instead of recreating or copying it.
- Extend an existing shared component only when the change remains backward
  compatible and genuinely reusable. Do not break existing consumers to satisfy
  one feature.
- If no suitable shared component exists, create a new widget under
  `lib/shared/` when it is required and represents app-wide design-system or
  reusable cross-feature behavior. Give it a focused, configurable API and add
  tests for meaningful behavior.
- Keep genuinely one-off or feature-specific UI under the feature's
  `presentation/widgets/` directory.

## REST API rules

The existing singleton `Dio` is the only REST client. It already uses
`AppConfig.baseUrl`, timeouts, JSON accept headers, a `ServerReachedInterceptor`
that tells `ConnectivityService` the server answered, and the debug-only
`HttpLoggerInterceptor`. Add cross-cutting request behavior (such as
authentication) through the `interceptors` parameter of `createDioClient`, which
runs before the logger. Use the registered singleton `LoggerService` for
application diagnostics; do not introduce direct `print` or `debugPrint` calls.
`LoggerService` writes each message or HTTP exchange as one block through
`dart:developer`, so logs appear in the IDE debug console and DevTools (not in
a terminal `flutter run`) without a per-line `flutter:` prefix.

Environment behavior is intentional:

- Release builds always use `PROD_URL`.
- Debug/profile builds use `DEV_URL` by default.
- Debug/profile use `LOCAL_URL` with `--dart-define=APP_ENV=local`, or when
  `DEV_URL` is missing, blank, or commented out while `LOCAL_URL` is set.
- `AppConfig.environment` exposes the resolved `AppEnvironment`.
- Additional hosts (sockets, CDNs) use `AppConfig.environmentUrl('<KEY>')`,
  which reads `PROD_<KEY>`, `DEV_<KEY>`, or `LOCAL_<KEY>` and falls back to the
  shared `<KEY>`. Do not write a second environment resolver.
- Never hardcode a host inside a feature data source.
- Endpoint paths may be constants local to a feature or a focused core endpoint
  definition; do not mix hosts with paths.

Before implementing an API, obtain or discover these details:

- Endpoint paths and HTTP methods
- Request body/query/path parameters
- Success status codes
- Exact response envelope and JSON fields
- Pagination shape, if any
- Authentication mechanism and token source
- Validation/error response shapes
- Whether delete returns content, `204`, or a soft-deleted object

If these details are not in the request, repository, API documentation, or
provided examples, ask concise questions. Do not invent production schemas.
Reasonable UI-only assumptions may be stated explicitly, but API-contract
assumptions require confirmation.

### Remote data source

Create an abstract contract and Dio implementation, for example:

```dart
abstract interface class ItemRemoteDataSource {
  Future<List<ItemModel>> getItems({int? page, int? limit});
  Future<ItemModel> getItem(String id);
  Future<ItemModel> createItem(CreateItemModel input);
  Future<ItemModel> updateItem(String id, UpdateItemModel input);
  Future<void> deleteItem(String id);
}

final class ItemRemoteDataSourceImpl implements ItemRemoteDataSource {
  const ItemRemoteDataSourceImpl(this._dio);

  final Dio _dio;

  @override
  Future<ItemModel> getItem(String id) async {
    final response = await _dio.get<Map<String, Object?>>('/items/$id');
    final json = response.data;
    if (json == null) {
      throw const FormatException('The server returned an empty item.');
    }
    return ItemModel.fromJson(json);
  }
}
```

Adapt parsing to the real response envelope. Validate nullable/optional values
at the boundary. Avoid unchecked `dynamic` chains and unsafe casts. A malformed
successful response must fail predictably instead of silently creating invalid
domain data.

### Models and entities

- Domain entities express business meaning and equality.
- Data models own `fromJson`, `toJson`, wire names, and mapping.
- Do not put `Dio`, `Response`, JSON maps, or transport-only fields in entities.
- Separate create/update input types when their required fields differ.
- Do not send server-managed fields such as IDs or timestamps unless required.
- Handwritten mapping is acceptable. Add code generation only when the project
  already uses it or the feature benefits enough to justify the dependency.

Example boundary:

```dart
final class ItemModel {
  const ItemModel({required this.id, required this.name});

  factory ItemModel.fromJson(Map<String, Object?> json) {
    final id = json['id'];
    final name = json['name'];
    if (id is! String || name is! String) {
      throw const FormatException('Invalid item response.');
    }
    return ItemModel(id: id, name: name);
  }

  final String id;
  final String name;

  Item toEntity() => Item(id: id, name: name);
}
```

### Repository and failure behavior

Define the repository interface in domain and implement it in data. Repository
methods return domain entities, never DTOs or Dio responses.

`core/errors/failure.dart` defines a sealed `Failure` hierarchy:
`ConnectionFailure`, `UnauthorizedFailure` (401), `ForbiddenFailure` (403),
`ValidationFailure` (field errors, 400, or 422, with `fieldErrors`),
`NotFoundFailure` (404), `ConflictFailure` (409), `ServerFailure` (other
statuses), and `DataFailure` (malformed data). `Failure.fromDioException` builds
the right type using `ApiErrorParser`, which understands `message`, `detail`,
`error` (including nested objects), `errors` as a list of `{field, message}` or
a field map, and top-level field arrays. Repositories may let a `DioException`
propagate or throw a `Failure` when they need API-specific mapping. Add a new
`Failure` subtype only for a category the UI must treat differently. Do not
parse error strings in widgets.

The provided `AsyncControllerMixin` already:

- Tracks named operations independently
- Emits immutable loading snapshots
- Guarantees operation cleanup
- Converts thrown `Failure`s and `DioException`s into a `ControllerError` with
  `message`, `isConnectionError`, `fieldErrors`, `statusCode`, and `failure`
- Classifies connection failures by Dio error type (timeouts and connection
  errors without a response), never by message text
- Falls back to a safe user-facing error for unexpected exceptions

Use it in feature BLoCs rather than duplicating `try/catch/finally` around every
event. Map `error.fieldErrors` into state to highlight form fields, and switch
on `error.failure` when a category needs distinct handling (for example
`UnauthorizedFailure`).

## CRUD BLoC design

Use explicit events. A typical CRUD feature may include:

```text
ItemsRequested
ItemRefreshRequested
ItemCreateSubmitted
ItemUpdateSubmitted
ItemDeleteRequested
```

Choose operation keys that allow independent progress indicators:

```text
items.load
items.refresh
items.create
items.update.<id>
items.delete.<id>
```

State should be immutable and `Equatable`. Preserve existing successful data
while a mutation runs. Do not replace an entire populated page with a global
spinner for one row’s delete operation.

A useful state normally contains:

- Load/status state
- Current immutable entity collection or detail
- `activeOperations`
- User-safe error information
- Field validation errors when returned by the API
- Pagination metadata when applicable

Use `AsyncControllerMixin<Event, State>`:

```dart
class ItemsBloc extends Bloc<ItemsEvent, ItemsState>
    with AsyncControllerMixin<ItemsEvent, ItemsState> {
  ItemsBloc(this._getItems) : super(const ItemsState()) {
    on<ItemsRequested>(_onRequested);
  }

  final GetItems _getItems;

  Future<void> _onRequested(
    ItemsRequested event,
    Emitter<ItemsState> emit,
  ) => runControllerTask<List<Item>>(
    key: 'items.load',
    emit: emit,
    task: _getItems.call,
    onLoadingChanged: (current, operations) => current.copyWith(
      activeOperations: operations,
    ),
    onSuccess: (current, items) => current.copyWith(
      status: ItemsStatus.success,
      items: List.unmodifiable(items),
      errorMessage: null,
    ),
    onFailure: (current, error) => current.copyWith(
      status: ItemsStatus.failure,
      errorMessage: error.message,
      isConnectionError: error.isConnectionError,
    ),
  );
}
```

Ensure `copyWith` can intentionally clear nullable errors. A sentinel-based
`copyWith`, explicit clear flag, or equivalent is safer than an implementation
where `null` ambiguously means both “retain” and “clear.” Collections stored in
state must not expose mutable references.

For create/update/delete success, update local state deterministically:

- Create: insert or append the server-returned entity according to sort order.
- Update: replace the matching ID with the server-returned entity.
- Delete: remove the matching ID only after confirmed success, unless an
  explicitly requested optimistic workflow includes rollback.
- Refresh: normally retain current content while showing refresh progress.
- Pagination: deduplicate by stable ID and prevent overlapping page requests.

Choose an event transformer deliberately if repeated events can race. Use
restartable behavior for search/type-ahead, droppable behavior for duplicate
page loads/submissions, and sequential behavior for ordered mutations. Do not
add a transformer package unless needed; use the APIs already available first.

## UI rules

- Before writing UI code, inspect `lib/shared/` and search for reusable buttons,
  text fields, selectors, loaders, cards, dialogs, snack bars, empty/error
  states, responsive wrappers, spacing helpers, and adaptive controls.
- Use the existing shared component when it satisfies the requirement. Do not
  create differently named duplicates with the same purpose.
- If a shared component is close but insufficient, prefer a small compatible
  extension or composition over copying its implementation. Add or update its
  tests when behavior changes.
- When no existing component can meet the requirement cleanly, create a new
  shared widget if it will be reused or belongs to the app-wide design system;
  do not force duplication merely to avoid adding a shared component.
- BLoCs do not own `BuildContext`, `TextEditingController`, `FocusNode`,
  `GlobalKey<FormState>`, dialogs, snack bars, or navigation.
- Stateful widgets own and dispose text/focus controllers.
- Widgets validate local form syntax; the API/domain validates business rules.
- Use `BlocBuilder`, `BlocSelector`, and `buildWhen` to limit rebuilds.
- Use `BlocListener` for one-time UI reactions and navigation.
- Never show snack bars or dialogs inside a repository, use case, or BLoC.
- Read per-operation loading state so create/update/delete controls disable only
  when their own operation is active.
- Provide loading, empty, populated, recoverable error, offline, and retry UI.
  For app-wide online state, listen to `ConnectivityService.isOnline` (a
  `ValueListenable<bool>`) instead of subscribing to connectivity_plus again.
- Prevent duplicate destructive submissions.
- Ask for confirmation before destructive deletion unless product requirements
  explicitly say otherwise.
- Preserve the generated design system. Material pages use Material controls;
  Cupertino pages use Cupertino controls and `CupertinoPageScaffold`.
- When both styles are supported by existing adaptive code, implement both.
- Keep pages focused; extract only meaningful feature widgets.

## Typography and fonts

- Use the `google_fonts` package for custom font families. Do not add font
  files under `assets/`, a `fonts:` section to `pubspec.yaml`, or `fontFamily`
  strings that depend on bundled files. If `google_fonts` is not yet a
  dependency, add it with `flutter pub add google_fonts`.
- Use a custom family only when the request or design names one; otherwise
  keep the platform default font. If a design clearly uses a custom font but
  does not name it, ask once.
- Apply the app-wide family once in `core/theme/app_theme.dart`, for every
  theme the project generates:
  - Material light: `textTheme: GoogleFonts.<family>TextTheme()`.
  - Material dark: pass the dark base,
    `GoogleFonts.<family>TextTheme(ThemeData(brightness: Brightness.dark).textTheme)`,
    so text keeps dark-mode colors.
  - Cupertino: `CupertinoTextThemeData(textStyle: GoogleFonts.<family>())`, and
    wrap any other Cupertino styles the app relies on (navigation titles, large
    titles, action text) with `GoogleFonts.<family>(textStyle: ...)` to keep
    their native sizes. `AppTheme.cupertino` becomes `final` instead of `const`.
- Widgets read styles from `Theme.of(context).textTheme` or
  `CupertinoTheme.of(context).textTheme` and adjust size, weight, height, and
  letter spacing with `copyWith`. Do not repeat the app font in individual
  widgets; call `GoogleFonts.<family>()` in a widget only for an element that
  uses a different family from the app font.
- When a design sample provides text styles, implement its size, weight, line
  height, letter spacing, and color exactly rather than adapting them to nearby
  screens.
- `google_fonts` downloads each font on first use and caches it on the device;
  until then, text renders in the fallback font. Do not set
  `GoogleFonts.config.allowRuntimeFetching = false`, because that requires
  bundled font files.
- macOS targets need the `com.apple.security.network.client` entitlement in
  both `macos/Runner/DebugProfile.entitlements` and `Release.entitlements` for
  fonts (and Dio requests) to download.
- Widget tests run without network access. `google_fonts` logs the failed
  download and falls back without failing the test; do not bundle fonts to
  silence that log.

```dart
static final materialLight = ThemeData(
  colorScheme: ColorScheme.fromSeed(seedColor: _seedColor),
  useMaterial3: true,
  textTheme: GoogleFonts.interTextTheme(),
);

static final materialDark = ThemeData(
  colorScheme: ColorScheme.fromSeed(
    seedColor: _seedColor,
    brightness: Brightness.dark,
  ),
  useMaterial3: true,
  textTheme: GoogleFonts.interTextTheme(
    ThemeData(brightness: Brightness.dark).textTheme,
  ),
);
```

## Splash screen

The profile's "Splash screen" row records the generated mode. Identify it from
`native_splash.yaml` and `lib/features/splash/` before changing launch
behavior.

- **None:** there is no `native_splash.yaml` and no `flutter_native_splash`
  dependency. The platform default launch screen shows.
- **Static:** `native_splash.yaml` sets `color`, `color_dark`, and
  `image: assets/splash/logo.png` (also under `android_12:`). `bootstrap()`
  calls `FlutterNativeSplash.preserve()` before async startup and `remove()`
  after `runApp`, so the native screen covers environment loading and
  dependency setup. There is no Flutter splash route.
- **Animated:** the native screen is color only. `/splash` is the router's
  `initialLocation`; `SplashPage` plays `assets/splash/splash_animation.json`
  once on the same color, then calls `context.go` with the result of
  `resolveNextRoute` (the playground when it is absent, returns `null`, or
  throws). `bootstrap()` prewarms the Lottie so its first frame is not blank.
  If the animation fails to load, `assets/splash/logo.png` shows for
  `SplashPage.fallbackDelay` before navigating.

Rules:

- Change native splash colors and images only in `native_splash.yaml`, then
  run `dart run flutter_native_splash:create --path=native_splash.yaml`. Never
  hand-edit the generated Android drawables, iOS launch storyboard/images, or
  web splash files.
- Keep `color`/`color_dark` in `native_splash.yaml` equal to
  `SplashPage.backgroundColor`/`darkBackgroundColor`. `SplashPage` follows the
  platform brightness, as the native screen does, not the app theme.
- `flutter_native_splash` stays in `dependencies`, not `dev_dependencies`,
  because `preserve`/`remove` run in the app.
- Splash logos are 960×960 PNGs with the artwork inside the central 640 px
  circle, which Android 12+ crops to. At 4x density this is 240 logical
  pixels; `SplashPage.logoSize` matches it so the hand-off does not jump.
- Replace `splash_animation.json` with the product animation; its
  transparent background shows the splash color. The page plays it for the
  composition's own duration.
- `SplashPage` enters `SystemUiMode.immersiveSticky` and restores
  `SystemUiMode.edgeToEdge` on dispose. Its `AnnotatedRegion` sets icon
  contrast for the splash color; the app root's region takes over afterwards.
- Resolve launch decisions (for example, a stored session) by passing
  `resolveNextRoute` from the router. Do not block `bootstrap()` on network
  calls to choose a route.
- Widget tests must load the Lottie in `setUp` with
  `AssetLottie(SplashPage.animationAsset).load()`; loading inside the test's
  fake-async zone never completes.
- To add a splash to a project generated with **None**, generate a throwaway
  project with the desired mode and port its `native_splash.yaml`,
  `assets/splash/`, `bootstrap.dart` changes, and (for Animated) the splash
  feature, route, and tests.

## Dependency injection and routing

Register dependencies in `configureDependencies()` from the outside inward:

```dart
getIt
  ..registerLazySingleton<ItemRemoteDataSource>(
    () => ItemRemoteDataSourceImpl(getIt<Dio>()),
  )
  ..registerLazySingleton<ItemRepository>(
    () => ItemRepositoryImpl(getIt<ItemRemoteDataSource>()),
  )
  ..registerLazySingleton(() => GetItems(getIt<ItemRepository>()))
  ..registerFactory(() => ItemsBloc(getIt<GetItems>()));
```

- Reuse the registered singleton `Dio`.
- Data sources/repositories/use cases are usually lazy singletons.
- BLoCs are usually factories unless their state intentionally spans routes.
- Dispose resources according to their registered lifecycle.
- Add route constants and `GoRoute`s to the existing `go_router` graph.
- Provide a route-level `BlocProvider` when the BLoC belongs to that route.
- Pass IDs through path parameters and short serializable filters through query
  parameters; fetch authoritative entities by ID rather than placing mutable
  objects in global state.

## Authentication, security, and logging

If authentication is requested:

- Discover the project’s token storage and refresh policy first.
- Add authentication centrally through a Dio interceptor passed to
  `createDioClient(interceptors: ...)`, not separately in every feature data
  source.
- Serialize concurrent refresh attempts and retry a failed request at most once.
- Never log access tokens, refresh tokens, passwords, authorization headers,
  personal information, or secret response bodies. `LoggerService` redacts keys
  ending in `token`, `password`, `secret`, or `apikey`, plus cookies, in
  headers, query parameters, JSON bodies, JSON strings, and multipart fields.
  Do not weaken this redaction; add a key pattern if an API uses another
  secret name.
- Do not place secrets in `.env` assets: Flutter asset values ship with the app.
- Treat client-side authorization checks as UX only; the server remains the
  authority.

## Testing requirements

Implement tests proportional to the change. For CRUD work, include:

1. Model parsing and serialization tests, including malformed JSON.
2. Remote data-source tests with a mocked/fake Dio adapter or equivalent.
3. Repository mapping and failure tests, including the expected `Failure`
   type for each documented error status.
4. Use-case delegation/business-rule tests.
5. `bloc_test` coverage for:
   - loading → success
   - loading → backend failure
   - connection failure classification
   - operation cleanup after every outcome
   - create/update/delete collection changes
   - concurrent keyed loading when applicable
6. Widget tests for loading, empty, populated, error/retry, and mutation states.
7. Both Material and Cupertino rendering when the generated project supports
   both paths.

Tests must assert meaningful states and behavior, not only that widgets exist.
Use fakes/mocks at architectural boundaries; do not call live production APIs.

## Execution workflow

For each request:

1. Restate the concrete outcome briefly.
2. Inspect the relevant existing implementation and API information.
3. Identify missing API-contract details; ask only blocking questions.
4. Make a small implementation plan for non-trivial CRUD work.
5. Implement vertically: domain → data → DI → BLoC → UI → route → tests.
6. Format changed Dart files.
7. Run code generation only if the project uses generated files.
8. Run `flutter analyze` and `flutter test`.
9. Fix failures caused by the change. Do not suppress legitimate lints.
10. Report changed behavior, important assumptions, tests run, and any remaining
    external dependency such as an unavailable backend.

Do not stop after scaffolding if the request asks for working CRUD. Do not leave
placeholder repositories, fake success responses, unregistered dependencies,
unreachable pages, or untested BLoC branches.
